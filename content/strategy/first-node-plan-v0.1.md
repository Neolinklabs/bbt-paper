# Babel Town 首批节点机制与商务方案

版本：v0.1 讨论稿。日期：2026 年 11 月 1 日。

本方案建议先组织具备持续供给能力的机构，形成可验收、可调度、可计量的资源池，再逐步扩大到更多机构和个人设备。“百万在线”覆盖供给实例、消费 Agent 和供需一体实例，按统一身份和时间窗口去重，不以单一 GPU 数替代网络规模。

本轮依据为[用户方向与任务](../../references/briefs/2026-11-01-direction.md)和[白皮书 v1.0](../whitepaper/whitepaper.md)。文中的首批数量、准入参数、分成和退出期限均为讨论建议；已明确的方向与尚待确认的商务承诺分开列示。

## 已明确的方向

- 目标是支撑百万在线，参与方式包括供给、消费和供需一体。
- 当前优先解决规模供给，由机构和数据中心形成首批资源，再带动分布式网络增长。
- 世纪互联将采购一批 GPU 加入网络，具体型号、数量、预算和交付批次尚未提供。
- 合作方侧重代码与产品迭代；我方侧重 GPU 资源、全球供给渠道和商务组织。

## 首批参与者与资源规模

### 优先发动的参与者

首批建议组织 3 至 5 家具有独立供给和运维能力的机构。这个数量用于控制联调复杂度，实际参与方以接洽和验收结果为准。

| 优先级 | 参与者 | 接入价值 | 当前状态 | 首次需要确认的内容 |
| --- | --- | --- | --- | --- |
| 第一批 | 世纪互联 | 以采购计划形成可组织的初始供给，并提供数据中心与运维协同 | 用户已明确采购方向，规模待定 | 采购主体、型号、卡数、部署位置、交付批次、运营和结算模式 |
| 第一批 | 我方现有渠道中的 GPU 数据中心或云算力运营商 | 接入已有资源，补充区域与硬件能力 | 候选类别，尚无已确认名单 | 可承诺资源、占用冲突、可用时段、成本和服务负责人 |
| 第一批 | 具备持续需求的企业或 Agent 平台 | 带入真实工作负载，也可贡献自有资源 | 候选类别，尚无已确认名单 | 模型、上下文、数据等级、调用规模、预算和自有算力 |
| 后续扩展 | 区域服务商、设备运营方和个人贡献者 | 扩大覆盖面，承接适合的推理任务 | 待首批规则验证后开放 | 标准接入、自助检测、反作弊和支持成本 |

优先接洽已有资源或近期确定交付、能够指定运维负责人、愿意提供试运行窗口的机构。商务团队首先拿到可执行的资源承诺和对应需求，再开展联合宣传。

### 资源规模的确认方式

不从“百万在线”直接倒推必须采购百万张卡。首批资源按服务画像组织：每类模型需要哪些硬件、量化方式、上下文长度、并发与延迟，再由需求量和实测能力决定部署数量。

| 资源池 | 本轮可确认的规模 | 立项前必须补齐的规模字段 |
| --- | --- | --- |
| 世纪互联初始资源池 | 将采购一批 GPU，具体数量待定 | 每批卡数、型号、显存、整机拓扑、地域、交付日、承诺服务时段 |
| 其他机构接入池 | 建议组织其他 2 至 4 家机构，资源数量待接洽 | 同上，并明确是否专供、共享、可抢占和已有客户占用 |
| 首批真实需求池 | 待确定种子客户或 Agent 应用 | 模型、峰值请求、Token 用量、并发、上下文和数据等级 |

原白皮书中的“32 张种子显卡”保留为历史草稿口径，不能替代本轮采购清单。采购计划、已交付、已安装、已验收和当前可服务五个状态分别记录。

## 首批节点的组织方式

对外使用“首批供给伙伴”身份，签署接入协议及资源附件。一个机构可以管理多个资源池和许多执行节点，机构身份、资源池和节点数量分别登记。

建议设立首批伙伴工作组，由供给伙伴、合作方技术负责人及我方资源与商务负责人参加。每个独立机构设一名代表，关联主体合并识别。工作组讨论接入标准、服务等级、计量规则及争议处理；正式决策权限以各方签署的协议为准。

Libra 的历史资料提供了首批机构组织、成员准入和共同规则的参考，详见[原始资料研究](../../references/libra-founding-nodes.md)。Babel Town 的机构供给、设备执行和用户调用需要各自的身份及规则，首批伙伴资格不自动意味着公司股权、永久否决权或排他供给资格。

## 准入门槛与权责

### 建议的首批准入条件

| 维度 | v0.1 建议门槛 | 验收或凭据 |
| --- | --- | --- |
| 主体与资源 | 可识别的签约主体，证明资源所有权或合法使用授权 | 主体资料、资源清单、授权或采购记录 |
| 最小交付 | 至少一个可独立验收的生产推理单元，承诺首轮提供 30 天服务 | 资源附件；多卡模型按整组验收，不能以单卡显存简单换算 |
| 技术接入 | 完成节点注册、认证、能力检测、模型服务与回执签名 | 合作方提供的接入测试记录 |
| 运行能力 | 指定运维和商务联系人，支持停机告知及故障响应 | 联系人与值班安排、故障演练记录 |
| 试运行 | 建议连续试运行 7 天，按约定测试窗口达到至少 99% 可用率 | 独立探测、请求记录与故障清单；生产 SLA 另行约定 |
| 性能与质量 | 达到双方事先约定的模型服务画像及一致性要求 | 模型版本、量化、上下文、吞吐、延迟、错误率和比对结果 |
| 计量与财务 | 能将请求、回执、账单与供给机构对应起来 | 日对账样本与差异处置结果 |

7 天和 99% 是首轮试运行建议，不作为已批准的对外承诺。模型性能阈值必须在测试前写入资源附件，不能以卡数或厂家标称性能替代。

### 参与者承担的责任与获得的权益

| 参与者 | 主要责任 | 建议权益或加入动机 |
| --- | --- | --- |
| 供给伙伴 | 按承诺提供资源，维护服务，接受准入与抽查，提供真实用量记录，配合退出迁移 | 接触聚合需求，按已确认服务获得合同约定对价，查看本方服务与对账记录，参与规则讨论 |
| 需求伙伴 | 提供真实应用及验收反馈，明确数据等级与预算，遵守服务约定 | 优先联调，获得适配资源和明确的数据路由规则；优惠额度由预算另批 |
| 合作方 | 交付接入、调度、产品、计量和可观测能力，处理软件问题 | 获得首批资源和真实负载，缩短产品验证周期；双方收益安排另行商定 |
| 我方 | 组织资源和渠道，推动商务、合同及运行协同 | 形成可持续供给渠道和服务业务；具体收入与责任边界写入合作协议 |

资源规模、质量、服务时段和需求匹配度影响实际调度。伙伴身份本身不保证订单、利用率或固定回报。联合品牌展示应在参与方同意后进行，未接洽的机构不列为已加入成员。

## 商务与结算建议

### 先确定每个资源池的交易模式

| 模式 | 资源与成本关系 | 需要明确的商务条款 |
| --- | --- | --- |
| 自购自营 | 指定主体承担采购、部署和运营成本 | 资产归属、运营方、服务收入归属及成本核算 |
| 租赁资源 | 按合同租用外部资源，再组织服务 | 租赁成本、可用时段、服务责任与收入分配 |
| 第三方供给接入 | 机构以已确认推理服务参与网络 | 服务单价或分成、结算主体、税费、账期和争议处理 |

同一资源池只按已约定的模式核算，避免租赁费与供给分成重复支付。

### 收益口径

白皮书 v1.0 提出请求费用的 70% 记给算力账户，积分默认确认期为 7 天。这些可作为首轮商务测算的起点，尚不能视为机构现金结算条款已确定。

建议用真实、已验收服务作为计量基础。对账中区分客户有效用量、系统抽查复算、失败重试、退款和促销抵扣。抽查产生的额外计算不重复记为客户消费。

若采用分成，可先按“可分配服务净收入 × 约定比例”测算；净收入是否扣除税费、退款、优惠及支付成本，抽查成本由谁承担，均需在合同中定义。不能从卡数或在线时长直接推算可兑现收入。

原稿标注积分兑付未开放。首批机构采用何种服务采购、应付账款或积分安排，是否需要系统隔离，以及由谁付款、开票和处理退款，需要运营、财务和法律审核形成明确方案后再签署；本方案不新增积分兑付承诺。

## 退出与异常处置

建议允许伙伴申请退出，常规退出提前 30 个自然日书面通知。退出前停止新增长期任务，按任务期限逐步排空，撤销调度资格与节点凭据，完成日志和账单核对。已确认服务的应付款按合同处理，争议部分单独列示，不因退出自动归零。

发生安全事件、资源授权失效或持续不达标时，先隔离受影响资源，保留证据并通知责任人。恢复、暂停或终止资格应有明确判据和复核渠道。作弊的证据标准、扣罚与申诉程序写入协议，不能仅凭一次不一致结果直接认定。

普通退出的通知期、在途任务最长等待时间、最后对账日、保证金安排以及提前解约责任均需在资源附件中确认。Libra 的历史退出规则仅作组织参考，不能代替这些算力服务条款。

## 技术接入与运行验收

### 从机构资源池到执行节点

沿用白皮书的节点、控制器、网关、中继和账本架构，在管理层补充机构和资源池映射：

`机构 → 资源池 → 物理设备 → GPU 或其他计算资源 → 执行节点 → 模型服务副本`

执行节点的数量由实现决定；多卡模型、副本、虚拟切片和进程重启均保留物理资源归属。资源池接入相同协议与验收体系，按服务画像、区域、数据等级和信任条件参与调度。

| 环节 | 合作方需要明确或交付的内容 | 我方与供给伙伴需要提供的内容 |
| --- | --- | --- |
| 注册与认证 | 主体、资源池、设备和节点 ID；证书签发、轮换及撤销 | 主体信息、资产或授权清单、管理员 |
| 网络与部署 | 节点主动连接方式、端口、代理、升级及回滚要求 | 部署环境、带宽、网络出口与维护窗口 |
| 能力与模型 | 硬件检测、引擎和模型版本、服务画像、许可证处理方式 | 实际资源与拟服务范围，模型使用授权信息 |
| 调度与隔离 | 硬约束过滤、负载和队列策略、容量预留、故障转移 | 专供或共享属性、已有占用、资源承诺和数据边界 |
| 计量与回执 | 双签回执格式、幂等去重、单位、时间及失败处理 | 财务对账要求、资源和账户映射 |
| 观测与支持 | 心跳、探测、告警、版本和审计接口 | 运行联系人、事件响应和证据保留安排 |

双签回执首先按原稿覆盖节点与网关签名。至少需要记录全局请求 ID、尝试 ID、回执 ID、机构与资源池、执行节点、模型版本、计量单位与数量、时间、最终状态、计费版本和抽查标记。资源核算另记设备及 GPU 分配区间；Token、图片数和音视频时长分别计量。

一次用户请求可有多次执行尝试。请求 ID 负责关联，尝试 ID 记录执行事实，账单幂等键防止重复收费；流式输出中断、切换节点和部分成功如何收费，须先达成规则。

### 首轮验收清单

1. 资源与身份：核对清单、授权和物理映射，验证重复注册不会重复增加资源规模。
2. 单池运行：完成模型加载、成功调用、流式响应、能力和质量测试。
3. 跨池调度：覆盖满载、断连、故障、数据等级拒绝和不满足区域条件的场景。
4. 计量对账：对成功、失败、重试、抽查和退款样本逐笔核对，重复回执不得增加收费。
5. 退出演练：停止接单、任务排空、凭据撤销和最终对账均可执行。
6. 试运行验收：完成约定观察期，记录性能、可用率、故障及未解决问题，由双方指定负责人确认。

### 通向百万在线的技术路径

第一步跑通上述业务闭环；第二步测试多机构、多资源池的隔离、扩缩容和观测；第三步按真实供需比例分批进行连接、心跳、调度、推理和计量压测，再做分区与故障恢复。

百万连接承载能力与百万实例同时执行推理需要分别验证。压测应报告供给与消费比例、心跳间隔、活跃率、模型负载及故障条件。若采用 30 秒心跳，100 万个实例仅心跳就约产生每秒 3.33 万个事件，尚未计入请求、回执和告警；这是容量估算，不是现有系统实测成绩。

## 百万在线统计口径

建议主指标命名为“90 秒窗口在线参与实例数”，以供给实例与消费 Agent 实例的统一 ID 并集计算，供需一体实例只计一次。机构数、用户数、物理设备数、GPU 数、模型副本数和并发请求数分别报告。

完整定义、去重规则、字段与验收示例见[百万在线统计口径 v0.1](online-metrics-v0.1.md)。在完成身份绑定、反重复注册和服务端真实活动验证之前，不对外宣称已达到这一指标。

## 推进分工与待决事项

| 工作 | 建议牵头方 | 本轮应形成的产物 |
| --- | --- | --- |
| 首批参与者与资源 | 我方资源和商务负责人 | 候选机构清单、世纪互联采购批次、资源附件、种子需求 |
| 产品与技术接入 | 合作方技术负责人 | 接入文档、字段协议、联调环境、测试与容量计划 |
| 商务与结算 | 双方商务、运营、财务及法律负责人 | 交易模式、收费和分配口径、签约及付款主体、退出条款 |
| 试运行与验收 | 合作方和各供给机构运维负责人 | 验收报告、对账样本、问题清单、扩大接入条件 |

以下决策影响首版能否进入实施：

- 首批具名机构及联系人是谁，哪些已经接洽，哪些仅为候选？
- 世纪互联实际采购什么、多少、何时交付，由谁持有并运营？
- 首批要承接哪些真实应用，需求规模和预算是什么？
- 采用哪种资源交易与结算模式，70% 和 7 天是否适用于机构合同？
- 谁确认模型服务画像、数据路由、SLA 与抽查比对标准？
- 双方是否接受参与实例的统计单位，以及何时、以什么负载验证百万目标？
- 用户提到的既有 Libra 材料是哪一版，与公开历史资料有何补充或差异？

首轮接入完成后，以真实服务、对账和退出演练结果决定扩展。扩展资源量随已验证需求调整，不以意向名单或采购计划代替可用供给。
