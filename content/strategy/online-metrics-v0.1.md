# Babel Town 百万在线统计口径

版本：v0.1 讨论稿。日期：2026 年 11 月 1 日。

建议把“百万在线”定义为同一 90 秒统计窗口内，满足认证、真实活动和去重要求的在线参与实例总数。参与实例可以只贡献资源、只消费服务，或同时供给与消费。该指标描述网络参与规模；资源能力和业务使用量同时单列报告。

依据：[用户方向](../../references/briefs/2026-11-01-direction.md)。以下窗口、ID 设计与校验规则为本方案建议，待与合作方对齐并实现。

## 统计对象与身份

| 对象 | 建议标识 | 统计用途 |
| --- | --- | --- |
| 机构或个人账户 | `principal_id` | 主体归属和权限；同一机构及其资源不能作为多个独立机构重复报告 |
| 人类使用者 | `user_id` | 独立统计活跃用户；不由 API Key、Agent 或设备数量推算 |
| 网络参与实例 | `participant_instance_id` | 百万在线主指标的统一单位，角色为供给、消费或供需一体 |
| 消费 Agent | `agent_instance_id` | 将稳定的 Agent 部署实例绑定到参与实例；进程重启和多个 API Key 不新建计数单位 |
| 物理设备 | `device_id` | 统计服务器或终端；重复安装、进程、虚拟机与容器不能重复贡献同一设备 |
| GPU 或资源分区 | `resource_id` 与物理父资源 ID | 记录卡数、显存和分配关系；切片、共享和副本不增加物理卡数 |
| 执行节点与模型副本 | `worker_id`、`replica_id` | 调度和运行观测；不直接作为物理设备或在线参与总数 |
| 请求、尝试与回执 | `request_id`、`attempt_id`、`receipt_id` | 统计并发、用量和结算，处理重试及重复上报 |

`participant_instance_id` 表示可识别的稳定部署实例，必须绑定归属主体和相应设备或 Agent 身份。同一部署实例同时供给和消费时使用同一个参与实例 ID。不同部署实例即使属于同一个账户，也分别登记，同时在主体级指标中合并。

一台设备可运行多个真实 Agent，但不能仅凭客户端自报进程或任意生成 UUID 就增加在线数。独立 Agent 部署的认定、配额、生命周期和异常批量注册检测需落地到注册服务及审计流程。该机制不能证明百万独立自然人，报告中应保留主体集中度。

## 主指标的集合定义

在统一服务端时间 `t`：

- `S(t)`：近 90 秒有有效心跳，且准入有效、未隔离，能够按约接单或正在执行有效任务的供给参与实例集合。每台物理设备最多对应一个供给参与实例；多 GPU 和多 worker 不增加该项计数。
- `A(t)`：已认证，近 90 秒有真实服务活动的消费参与实例集合。活动包括可核验的成功模型调用，或仍在执行且持续有进展的有效请求；仅刷新心跳、失败鉴权和健康探测不计入。
- `B(t)`：`S(t)` 与 `A(t)` 的交集，即同一个参与实例同时满足供给与消费条件。

```text
online_total(t) = count_distinct(S(t) ∪ A(t))
                = |S(t)| + |A(t)| - |B(t)|
```

这是按 90 秒活动窗口定义的在线快照。它不能直接解释为同一瞬间执行中的请求数；同时报告单独的推理并发指标。建议每 10 秒生成一次快照，所有集合使用同一快照时间和指标版本。

供给设备上的独立消费 Agent 如确有单独部署身份，可以另计一个参与实例；同一部署单元的供需两个角色必须绑定合并，不能以两个角色名称多计一次。需要双方先确认“独立部署实例”的执行规则，再将此口径用于对外报告。

## 资源与用量另列

| 指标 | 口径 |
| --- | --- |
| 在线机构数 | 在线实例所属的去重机构数，关联主体处理规则另行公示 |
| 活跃账户与人类用户 | 分别按主体和用户去重；时间窗口明确标注 |
| 在线物理设备数 | 按物理父设备归并，多卡服务器计一台；独立供给设备按自身物理身份登记 |
| 在线 GPU 数 | 按物理卡去重，另报型号、显存、地域与可用时段 |
| 可调度与执行中资源 | 分开报告空闲可接单、执行中、维护及隔离状态；满载执行的健康设备仍可在线 |
| 消费 Agent 数 | 去重的在线或活跃 Agent 部署数；不等于人类用户数 |
| 推理并发请求数 | 快照时刻处于有效执行状态的唯一请求数，重试尝试另计 |
| 有效业务用量 | 客户成功用量中的输入 Token、输出 Token、图片及音视频时长分别报告 |
| 系统额外用量 | 抽查、基准测试、失败重试等单列，不能混入真实客户消费 |

不同显存和不同模型服务能力不折算成一个未经定义的“等效 GPU”数字。共享卡的多个切片计一张物理卡；可调度容量还要扣除已承诺给其他服务的占用。

## 去重与数据质量规则

1. 机构资产清单、设备密钥与可验证硬件信息绑定物理身份；密钥轮换、系统重装和 Agent 重启保留历史映射。硬件信息不能单独作为不可伪造的身份证明。
2. 服务端签发或确认参与实例 ID。别名及供需角色映射先归一，再做集合运算；历史映射变更可追溯。
3. 心跳与活动事件携带唯一事件 ID、服务端接收时间、序列号、状态和来源。重复或乱序事件不得扩大统计数，补报历史活动不制造当前在线。
4. 测试、机器人压测、内部抽查、健康探测和生产流量分别标记。模拟百万实例的结果报告为容量测试，不能作为百万真实参与者。
5. 快照输出供给数、消费数、交集、并集、机构集中度及异常排除数。缺少关键身份映射的事件进入待核对集合，不纳入已核验主指标。
6. 禁止只依赖客户端计数。机构供给核对资产和资源分配，Agent 活动核对服务端请求与回执；批量注册和重复硬件设人工复核通道。

## 最小数据字段

每次用于在线统计的事件至少包括 `event_id`、`metric_version`、`participant_instance_id`、`principal_id`、角色、服务端时间、事件类型和状态。供给事件补充设备及资源映射、准入与隔离状态；消费事件补充 Agent、有效请求或回执引用，以及生产或测试标记。

统计数据不需要保存提示词或回答。对外披露汇总指标，明细映射限定访问权限和保留期限；个人及机构标识不直接公开。

## 验收示例

| 场景 | 主指标期望结果 | 资源与业务指标 |
| --- | --- | --- |
| 一台 8 卡服务器运行 8 个 worker | 1 个供给参与实例 | 1 台设备、8 张 GPU、8 个 worker |
| 同一参与实例同时供给并消费 | 总数增加 1，供给和消费各有记录，交集为 1 | 双方用量依实际任务计量 |
| 同一 Agent 重启并换用另一个 API Key | 仍为 1 个消费实例 | 请求可以有多条 |
| 100 个供给实例、200 个消费实例，其中 30 个为同一供需实例 | 去重总数 270 | 各分类数与交集同时展示 |
| 设备失联超过 90 秒 | 从当前供给在线集合移出 | 历史在线及使用量保留 |
| 同一请求重试，重复上报回执 | 不因重试增加参与实例数 | 保留尝试记录，账单按幂等规则处理 |
| 生产设备满载，任务持续正常执行 | 设备仍计在线，空闲容量为零 | 执行中资源与请求并发增加 |
| 模拟百万实例发送心跳 | 进入独立压测指标 | 不进入真实生产在线数 |

试运行时用固定事件集校验上述结果，再检查迟到事件、时间漂移、重装、身份别名变更、共享 GPU 和跨区域快照的一致性。主指标确认后再冻结首个统计版本。
